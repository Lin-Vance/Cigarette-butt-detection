## 一、架构过配判定（8 项）

部署级别是**校园试点（2-4 路摄像头）**，以下组件与服务规模不匹配，判定为过配。

| # | 组件 | PRD 定位 | 修订结论 | 替代方案 |
|---|------|----------|----------|----------|
| 1 | InfluxDB 2.x | 时序数据库，按小时/天/周聚合 | 砍掉 | PostgreSQL 单表 + `date_trunc` 聚合；试点数据量下性能绰绰有余 |
| 2 | MinIO | 对象存储，存视频片段与关键帧 | 降级为本地目录 | `storage/evidence/` 目录 + FastAPI `StaticFiles`；省一套服务与 S3 SDK |
| 3 | Redis 7 | 环形缓冲区索引 / WS 会话 / 限流 | 降级 | 进程内字典 + `asyncio` 锁；限流可用 `slowapi` |
| 4 | Redis Streams | AI→后端事件消息队列 | 砍掉 | 直接 HTTP POST + 指数退避重试（PRD 已设计的备通道机制足够） |
| 5 | K8s + Helm | 后续扩展编排 | 砍掉 | 本地 `uvicorn` 单进程启动；答辩演示无需容器编排 |
| 6 | Docker 四镜像 | 交付物第 5 项 | 降级为 1 个 | 单 `Dockerfile` 或直接提供 `start.bat` / `start.sh` |
| 7 | 微信小程序 | 移动端 4 个页面 | 砍掉 | H5 移动页（同一 Vue 工程的移动路由）；答辩讲述时说明"预留 H5 形态" |
| 8 | ReID 跨摄像头追踪 | PRD §4.4 创新点之一 | 降级为显式限制 | 若只部署 2-4 路且画面不重叠，跨摄像头接力无实际收益；文档中改述为"预留多路扩展能力" |

**保留不动**：FastAPI 后端、PostgreSQL、WebSocket 实时推送（PRD §5.4.2）、RBAC 权限矩阵（FDD §4.1.2）。

## 二、逻辑缺陷（21 项）

### A. AI 算法管道（11 项）

#### A1 · 检测类别表缺 person，导致跟踪模块整体失效 《严重》

- **位置**：FDD L593 `self.classes = {0: "cigarette", 1: "hand"}`
- **冲突**：`data.yaml` 为 `nc: 3, names: ['cigarette', 'hand', 'person']`，即 `2 → person`。
- **引用点**：FDD L981 `person_dets = [d for d in detections if d["class"] == "person"]` —— ByteTrack 只吃 person 检测。
- **后果**：模型输出的 person(2) 被 `self.classes.get(cls, "unknown")` 映射成 `"unknown"`，`person_dets` 恒为空列表 → ByteTrack 拿不到任何目标 → **§3.5 跟踪与事件关联模块全链路失效**，PRD §4.4「时空关联全要素追溯」创新点无法实现。
- **修订**：`self.classes = {0: "cigarette", 1: "hand", 2: "person"}`；并增加启动期断言 `assert len(self.classes) == self.model.model.nc`。

#### A2 · ROI 开启后所有检测框坐标错位 《严重》

- **位置**：FDD L643-651 `_apply_roi()`；被引用处 FDD L614、L630-635
- **问题**：`masked = cv2.bitwise_and(frame, frame, mask=mask)` 输出**与原图同尺寸**，并未裁剪。但函数返回 `(x_min, y_min)` 作为偏移量，`detect()` 又把该偏移**加上**到 bbox 上：`int(x1 + offset[0])`。
- **后果**：ROI 内检测框被二次平移，全部错位；且 ROI 没有起到"缩小搜索区域"的作用（性能收益也为零）。
- **修订**：要么真裁剪（`frame[y_min:y_max, x_min:x_max]` 后再推理，偏移加上去才正确），要么保持全图推理并**删除偏移量回加逻辑**。二选一，不可混用。

#### A3 · LANDED 是死状态，`_handle_landed()` 永不可达 《严重》

- **位置**：FDD L812-815、L820-822、L888
- **问题**：`_handle_throwing()` 中
  ```python
  if ctx.landed_static_count >= self.config.landed_min_static_frames:
      ctx.stage = EventStage.LANDED
      return self._generate_event(ctx)        # ← 立即返回
  ```
  而 `_generate_event()` 末尾（L888）执行 `self._reset_to_idle(ctx.track_id)`，把 `contexts[track_id]` 整个替换为新的 `TrackContext`（L939）。stage 停留在 LANDED 的时间为 0 帧，**`_handle_landed()`（L820-822）在任何输入下都不会被执行**。
- **连带**：PRD §4.3 状态机图与 FDD §3.7 流程图都画了独立的 `THROWING → LANDED → CONFIRMED` 两跳，与代码的单跳自相矛盾。
- **修订**：`_handle_throwing` 命中静止帧数后**只改 stage 不生成事件**，交由 LANDED 分支处理；或在文档中承认 LANDED 与 CONFIRMED 是同一帧内的原子转换，删除 `_handle_landed()` 与流程图中多余的边。

#### A4 · 三张关键帧一张都传不出去，而事件仍能通过校验 《严重 · 最高优先级》

- **位置**：FDD L866-889（`_generate_event`）、L1078-1097（`EvidenceCollector.collect`）、L1412-1455（`_validate_evidence_chain`）
- **链条**：
  1. `_generate_event()` 在 L888 调用 `_reset_to_idle()` → `contexts[track_id]` 被替换为全新对象，`holding_best_frame` / `throwing_best_frame` / `landed_best_frame` 全部变成 `None`。
  2. `EvidenceCollector.collect()` 在 L1078 用 `state_machine.contexts.get(event["track_id"])` 取上下文 → 拿到的是**已被重置的新对象** → L1088 `frame_data = frame_map.get(...)` 全为 `None` → `if frame_data:` 判空跳过 → **三张关键帧一张都不写盘、不上传**。
  3. `event["evidence_frames"][i]["path"]` 全部保持为 `None`。
  4. `_validate_evidence_chain()` 只校验帧的**数量**（`len(frames) != 3`，L1419）与**类型集合**（L1424-1426），**不校验 `path` 是否为空**。
- **后果**：违规事件照常入库、照常生成工单、照常推送报警，但前端「证据追溯面板」的三帧证据与缩略图**全是空图**——正好砸在 PRD §1.3 核心创新点「三段式行为证据链」的可视化上。
- **修订**：(a) `_generate_event()` 改为**先采集证据、后重置状态机**，或在生成事件时就深拷贝三帧数据进 payload；(b) `_validate_evidence_chain()` 增加 `if not f.get("path"): return invalid`。

#### A5 · 环形缓冲区帧率写死 25，且"前后各 10 秒"物理上不可能

- **位置**：FDD L494-505（`extract_clip`）、L1116-1123（`_encode_video`）
- **问题一**：`clip_size = int((before_seconds + after_seconds) * 25)` 硬编码 25，忽略构造函数里的 `self.fps`（L480）。自适应抽帧会把帧率降到 15 FPS（L431），此时片段时长与播放速度都偏离预期；`_encode_video` 同样写死 `cv2.VideoWriter(..., 25.0, ...)`。
- **问题二**：`extract_clip` 只能取缓冲区**末尾**的 `clip_size` 帧（L504-505），即全部是**触发时刻之前**的帧。触发时未来帧尚未产生，所谓"前后各 10 秒"在实现上无法成立，实际最多拿到触发前的 ~20 秒。
- **修订**：改用 `self.fps` 计算并传入编码器；文档中把表述改为"截取违规时刻**之前 20 秒**的缓冲视频，触发后继续录制 10 秒并二次合并'"，或直接改述为"前 20 秒"。

#### A6 · 超时判断用墙上时钟，离线处理视频文件时完全失真

- **位置**：FDD L925-934（`_check_timeout`）、L758/L788（`stage_enter_time = datetime.now()`）
- **问题**：`process_frame()` 接收帧 `timestamp` 参数（L713）却从不用于计时；超时全部基于 `datetime.now()`。离线跑视频文件时，一帧的处理速度远快于 / 慢于真实时间流速 → HOLDING 的 10 秒超时、THROWING 的 2 秒超时会大规模误判（快速处理时全部超时回退，逐帧慢放时全部不超时）。
- **连带**：`datetime.now()` 是无时区的本地时间，与 PRD §7.3「时间格式统一使用 ISO 8601 **带时区**格式」冲突（详见 C3）。
- **修订**：`stage_enter_time` 改存帧时间戳（或其解析后的 `datetime`），超时统一按帧时间轴计算。

#### A7 · 抛物线拟合的输入分辨率不足以支撑 R² 判据

- **位置**：FDD L824-848（`_check_throwing_action`）、L850-864（`_fit_parabola`）、L913-923（`_is_static`）
- **问题**：烟头在监控画面中仅 10-20 像素（PRD §4.2）。而 `_is_static()` 判定"静止"的阈值是最近 3 帧位移 **< 3 像素**——即认为 3 像素以内的抖动都是静止。在同一量级上，`_fit_parabola` 对 `(x, y)` 像素点做二次拟合并宣称 `R² > 0.85` 作为"主动抛掷"判据，实际会被检测框抖动主导，**该判据不具备判别力**。
- **修订**：改为对**亚像素级质心**（如 bbox 加权质心 + 光学流位移场）拟合，并放宽为"R² ≥ 0.7 且拟合得到的初速度方向与重力夹角 < 45°"的**组合**判据；或在文档中明确此项为"实验室条件下验证、工程实现留待后续"。

#### A8 · 综合置信度只用了 2 个因子，与注释不符

- **位置**：FDD L891-895
- **问题**：注释写"综合置信度：持烟持续帧数 + 抛掷速度 + **拟合优度**"，代码只有 `holding_score` 与 `velocity_score` 两项加权（0.4 / 0.6），`_fit_parabola` 算出的 R² 完全没进入置信度。
- **修订**：补充 `fit_score` 项并重新分配权重，或修正注释。

#### A9 · 状态机上下文仅以 track_id 为键，多路摄像头互相污染；且无锁

- **位置**：FDD L710 `self.contexts = {}  # {track_id: TrackContext}`
- **问题**：track_id 由 ByteTrack 在**单路视频内**分配，必然跨摄像头重复。若多路共用同一个状态机实例（§3.7 主流程未明确为每路创建独立实例），cam_A 的 track_id=5 与 cam_B 的 track_id=5 会命中同一条上下文 → 状态串台、证据帧张冠李戴。
- **连带**：`contexts` 字典无锁。对比 `CircularFrameBuffer` 明确加了 `threading.Lock()`（L484），同一份文档内标准不一致。多路拉流线程并发读写该字典不安全。
- **修订**：键改为 `(camera_id, track_id)`；或明确"每路摄像头一个 `EvidenceChainStateMachine` 实例"并写进 §3.7；补锁。

#### A10 · "双重匹配"的时间窗口部分是空实现

- **位置**：FDD L1040-1044 `_calc_temporal_overlap()` 直接 `return 0.5`
- **问题**：PRD §4.4 与 FDD §3.5 都宣称"空间匹配 + 时间窗口匹配"双重策略。实际时间窗口没有任何计算，返回常量。于是 `associate_event()` 的排序（L1029-1036）**退化为纯距离排序**。
- **连带**：`_estimate_hand_bbox()`（L1046-1049）用"行人框上方 1/3"**几何估算**手部，而模型本身能检测 `hand` 类（A1 已修）。真实手部检测框被弃用，改用估算框，精度下降。
- **修订**：要么实现真实的时间窗口重合计算（手部轨迹与烟头轨迹在 `[t-Δt, t+Δt]` 内的最近距离），要么在文档中把该创新点改述为"基于空间距离的关联"，不要同时声称"双重"。

#### A11 · 关联得分上限只有 0.5，距离阈值 100 形同虚设

- **位置**：FDD L1033、L1038
- **问题**：`score = 0.5`（A10 的常量）× `(1 - dist/100)`，最大 0.5；再要求 `best_score > 0.3` → 等价于 `dist < 40px`。函数参数中宣称的 `d_threshold = 100 像素` 实际不起作用，且 `score > 0.3` 这个魔法数与 0.5 的常量强耦合，A10 一旦修好，此阈值立即失效。
- **修订**：把阈值与距离阈值解耦，用一个显式的 `min_association_score` 配置项。

### B. 后端服务（10 项）

#### B1 · 刷新 Token 接口 100% 不可用 《严重》

- **位置**：FDD L1238-1253，关键行 **L1253** `return self.login(user.username, user.password_hash)`
- **问题**：`login()`（L1190-1197）内部执行 `self._verify_password(password, user.password_hash)`。此处传入的 `password` 是 **bcrypt 哈希串本身**，拿哈希去比对哈希，必然 `False` → 抛 `InvalidCredentialsError`。
- **后果**：PRD §5.4.3 承诺的"Refresh Token 有效期 7 天"完全无法兑现，Access Token 2 小时一过用户必须重新登录。
- **修订**：
  ```python
  def refresh_token(self, refresh_token: str) -> dict:
      payload = jwt.decode(refresh_token, self.secret_key, algorithms=[self.algorithm])
      if payload.get("type") != "refresh":
          raise TokenInvalidError("Token 类型错误")
      user_id = int(payload["sub"])
      if self.redis.get(f"refresh:{user_id}") != refresh_token:
          raise TokenInvalidError("Refresh Token 已失效")
      user = self.user_repo.get_by_id(user_id)
      if not user or user.status != "active":
          raise AccountDisabledError("账户已禁用")
      # 直接签发，不再走 login()
      return self._issue_tokens(user)
  ```
  即抽出 `_issue_tokens(user)` 供 `login()` 与 `refresh_token()` 共用。

#### B2 · refresh_token 中 user_id 类型不匹配

- **位置**：FDD L1247 `user_id = payload["sub"]`（字符串）→ L1252 `get_by_id(user_id)`
- **修订**：`user_id = int(payload["sub"])`。

#### B3 · 幂等实现非原子，且阶段事件与确认事件共用同一个键

- **位置**：FDD L1380-1386、L1408
- **问题一（竞态）**：先 `redis.exists` 检查（L1380）、末尾才 `setex` 标记已处理（L1408）。两个并发重试会同时通过检查 → **重复建单、重复推送**。
- **问题二（键冲突）**：非 CONFIRMED 阶段写的是**同一个键** `event:{event_id}`，TTL 300 秒（L1385）。一旦 AI 侧用同一 event_id 先发阶段事件、再发 `THROW_CONFIRMED`，确认事件会被 L1380 判为已存在并返回 `{"status": "duplicate"}` **直接丢弃**。
- **修订**：改用原子写入 `SET key value NX EX ttl`，以返回值判断是否为首次；阶段事件与确认事件改用不同键前缀（如 `event:stage:{id}` / `event:confirmed:{id}`），或干脆不缓存阶段事件。

#### B4 · ORM 层整体缺失，并引用了未定义的关系属性 《严重》

- **位置**：FDD **L1465** 与 **L1613** 两处 `event.evidence_frames[0].file_path`
- **问题**：全文检索确认——功能设计文档**没有任何 SQLAlchemy 模型定义**（无 `declarative_base`、无 `class ViolationEvent`、无 `relationship(`）。虽然 §6.1 有 ER 图、§6.2 有建表 SQL，但 ORM 层完全没写。`ViolationEvent` 上不存在 `evidence_frames` 属性 → 运行时 `AttributeError`。
- **连带**：`evidence_files` 是独立表（多对一），即使定义了 relationship，`[0]` 也不保证是"持烟帧"，缩略图可能取到落地帧。
- **修订**：补写 ORM 模型层，显式定义 `ViolationEvent.evidence_files` 关系；缩略图改为按 `file_type == "holding_frame"` 查询，而非依赖列表下标。

#### B5 · 决策引擎的依赖未注入，一进规则即崩溃 《严重》

- **位置**：FDD L1802-1812（`__init__`）、L1824、L1834、L1838、L1873、L1875
- **问题**：构造函数只接收并保存 `stats_service` 与 `suggestion_repo`：
  ```python
  def __init__(self, stats_service, suggestion_repo):
      self.stats = stats_service
      self.repo = suggestion_repo
      self.rules = [...]
  ```
  但规则体里使用了 **`self.camera_repo`（L1834）**、**`self.event_repo`（L1838、L1873）**、**`self.ws_manager`（L1824）**、`self.stats_service`（L1804 只存成了 `self.stats`）——四个属性全部未定义。
- **后果**：`check_and_generate_suggestion()` 第一次被调用就 `AttributeError`，PRD §5.3.3「调度规则引擎」与 PRD §6.3「调度建议卡片」整体不可用。
- **修订**：补齐依赖注入，统一命名（注意 `self.stats` 与 `self.stats_service` 两种写法并存）。

#### B6 · 决策规则的量纲不一致，规则要么恒触发要么永不触发

- **位置**：FDD L1838-1842（增设设施）、L1873-1878（调整排班）
- **问题**：
  ```python
  area_events = await self.event_repo.count_by_area(area, days=7)     # 近 7 天「计数」
  avg_events  = await self.event_repo.avg_by_area_last_30_days(area)  # 近 30 天「均值」
  threshold = avg_events * 1.5
  if area_events > threshold and area_events > 5:
  ```
  两者量纲不同。若 `avg_by_area_last_30_days` 返回**日均值**，则 7 天计数天然约为它的 7 倍 → 条件**恒成立**，建议卡片会对每个区域无限刷出。若返回的是 30 天**总量均值**，阈值远高于 7 天计数 → 条件**恒不成立**，规则永不触发。两种解释下都不可用。
- **连带**：L1849 `pct = int((area_events - avg_events) / avg_events * 100)` 因此也是无意义的百分比，却会被写进给用户看的建议文案（L1853-1855）。
- **修订**：统一到同一时间窗与同一统计口径。建议方案：
  ```python
  recent_daily = await self.event_repo.count_by_area(area, days=7) / 7      # 近 7 天日均
  baseline_daily = await self.event_repo.avg_by_area_last_30_days(area)     # 近 30 天日均
  if baseline_daily > 0 and recent_daily > baseline_daily * 1.5:
  ```
  `_rule_adjust_schedule` 同样处理。

#### B7 · 时段字符串在 23 点越界

- **位置**：FDD L1870 `hour_str = f"{hour:02d}:00-{hour+1:02d}:00"`
- **问题**：`hour=23` 时输出 `"23:00-24:00"`，而"24:00"不是合法时刻，且会被写入建议文案（L1888）与 `get_pending_by_time_and_type` 的匹配键（L1879）。
- **修订**：`end_hour = (hour + 1) % 24`，或在文案中特判为 `23:00-次日 00:00`。

#### B8 · `_validate_evidence_chain()` 名不副实，且放过空证据

- **位置**：FDD L1412-1455
- **问题一**：PRD §5.2.1 声称校验"三段式完整性：检查 HOLDING → THROWING → LANDED → CONFIRMED **四阶段是否齐全**"。但函数实际只检查 `evidence_frames` 的**数量**（L1419）与**类型集合**（L1424-1426）。事件 payload（PRD §7.1）里根本没有任何阶段转移记录字段，"四阶段齐全"无从校验——**承诺与实现不匹配**。
- **问题二**：不校验各帧的 `path` 是否为空。配合缺陷 A4，**证据全空的违规事件可以顺利通过校验并入库**。
- **修订**：(a) 在事件协议中补 `stage_transitions: [{stage, ts}, ...]` 字段并按序校验；(b) 立即补 `path` 非空校验；(c) 若选择不实现四阶段记录，则同步修改 PRD §5.2.1 的表述。

#### B9 · 每条事件串行跑 4 条规则，约 9 次聚合查询

- **位置**：FDD L1814-1827（循环）、L1838-1839、L1873-1875
- **问题**：`check_and_generate_suggestion()` 对每条违规事件**串行**执行 4 条规则；每条规则又发起多次跨表聚合：`count_by_area`、`avg_by_area_last_30_days`、`count_by_hour`、`avg_hourly_last_30_days`、`count_total`，合计约 9 次聚合查询。这些全部阻塞在事件处理链路（`_trigger_post_event_flow`，L1476）上。
- **修订**：改为定时任务（如每 10 分钟或每日）批量评估规则，而不是每条事件触发一次；聚合结果加缓存。

#### B10 · KDE 未做纬度投影修正，热区被东西向拉扁

- **位置**：FDD L1783-1794 `_kde()`
- **问题**：`distances = np.sqrt(np.sum((data_points - gp) ** 2, axis=1))` 直接在 `(lat, lon)` 二元组上计算欧氏距离。信阳约 32°N，**1° 经度的地面距离 ≈ cos(32°) ≈ 0.848 × 1° 纬度**。于是核函数在真实地面空间是一个约 1.18 : 1 的椭圆，**热力图会在东西向被拉长**——而热力图正是 PRD §6.3「决策驾驶舱」的核心视觉。
- **连带**：L1766 注释 `bandwidth = 0.0003  # 约 30 米（经纬度）`，但 0.0003° 纬度 ≈ 33 米、0.0003° 经度 ≈ 28 米，注释本身已暴露该问题。L1792 归一化后再用固定阈值 `0.01` 过滤（L1772），阈值实际是相对值，与"密度"语义不符。
- **修订**：先把经纬度投影到局部平面（等距圆柱或 UTM），再算距离：
  ```python
  lat0 = coords[:, 0].mean()
  kx = np.cos(np.radians(lat0))          # 经度方向压缩系数
  pts = np.column_stack([coords[:, 1] * kx, coords[:, 0]])   # (x_m, y_m) 近似
  ```
  归一化与阈值过滤分开，过滤用归一化前的密度值。

### C. 口径与一致性（4 项）

#### C1 · K8s Helm 的"可选"与"必经"自相矛盾

- **位置**：PRD §11 交付物清单第 7 项标注"（可选）"；PRD §12 里程碑"五、系统集成与测试"把 Helm Chart 列为该阶段交付物。
- **修订**：按本说明第一节判定，K8s/Helm 整体砍掉，从交付物清单与里程碑中同时移除，改为"预留容器化部署说明"。

#### C2 · 演示数据量级与试点规模不符

- **位置**：设计稿页面 2 显示"今日违规事件 1,286""在线设备 3,842""在线人员 684"；PRD §3.3 部署级别为"校园试点（2-4 路摄像头）"。
- **问题**：4 路摄像头不可能产生 1,286 次/日的违规事件，设备数 3,842 与 2-4 路直接冲突。评审现场极易被质疑数据真实性。
- **修订**：全站演示数据调整到与试点匹配的量级（建议：在线设备 4、今日违规 12-30、在线人员 3-8、工单 0-5），并在页面显著位置标注"演示数据"。**待用户确认具体数值。**

#### C3 · 时间格式与 PRD §7.3 的强制约定冲突

- **位置**：FDD L870 `datetime.now().isoformat()`、L758/L788/L929 同样使用无时区的本地时间；PRD §7.3 要求"统一使用 ISO 8601 **带时区**格式（`2026-08-07T22:10:35.123+08:00`）"。
- **修订**：统一使用 `datetime.now(timezone(timedelta(hours=8)))` 或 `ZoneInfo("Asia/Shanghai")`。

#### C4 · 三套并行方案未收敛（技术栈冲突）

- **位置**：PRD §3.2 定 Vue3 + TypeScript + Vite + Element Plus；FDD §2.4 给出 `src/views/...` 目录树；而 `smoke-admin/` 现有 18 页是**定宽 1672×941 + fit-shell JS 缩放**的原生 HTML/CSS/JS，且 `smoke-admin/README.md` 记录的 v2–v4.1 全部交互（yz-dd v4 下拉、壳页 `#sub`/`#embed`）都基于原生实现。
- **问题**：两份文档与现有资产是三套互不兼容的方案，且 PRD 的技术栈意味着 18 页全部重写、v2–v4.1 四轮打磨作废。
- **修订**（经 2026-09-23 决策）：**采用 Vue3 + Element Plus 工程化重写**（路线 B），但**强制约束**：
  1. 现有 18 页的视觉（配色、间距、圆角、图标语义）是**视觉规范来源**，Element Plus 只提供行为（分页、校验、弹窗），外观必须按现有设计稿覆盖，**不得退回 EP 默认外观**；
  2. 保留 1672×941 定宽 + 等比缩放策略，以布局组件（`FitShell`）形式继承，确保答辩投影不崩版；
  3. 复用现有 86 张 PNG 资源（品牌 logo、地图底图、摄像头缩略图、图标）。

### 模拟数据引擎要求（因 AI 侧未实现）

由于三段式状态机、ByteTrack、光流法、抛物线拟合均未实现（用户 2026-09-23 确认），后端需内置一个**合规事件生成器**：

1. 生成的事件 JSON 必须**完全符合 PRD §7.1 协议**，且通过修订后的 `_validate_evidence_chain()`（含 `path` 非空校验）；
2. 三段式证据帧用真实图片素材合成（持烟帧 / 抛掷帧 / 落地帧），不能留空——否则正好复现缺陷 A4 的观感问题；
3. 需提供"**一键演示一次违规**"接口，供答辩现场可控触发完整链路：事件生成 → WebSocket 推送 → 告警列表新增 → 自动建单 → 调度任务池出现 → 采纳建议 → 工单闭环；
4. 数据量级按 C2 修订值，并在前端标注"演示数据"。

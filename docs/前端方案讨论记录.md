## 1. 申报书能够支持到什么程度

### 已有证据支持

- 已训练 YOLOv8n 三类别模型（香烟、手部、行人）。
- 申报书记录了 1139 张图像上的目标检测指标：总体 mAP50 84.4%、mAP50-95 52.4%，香烟类别 mAP50 82.2%。
- 已提出“持烟—抛掷—落地”的三阶段状态机、行人关联和证据归档方案。

### 尚不能直接宣称

- 尚无独立视频与身份标注证明完整乱扔行为识别准确率。
- 尚无事件级真值视频，因此不能把单帧目标检测 mAP 表述成“行为识别准确率”。
- 行人关联、多人遮挡、烟头落地后的可见性、跨场景鲁棒性仍待验证。
- 现有约 2.6 ms 记录仅是 GPU 批处理下的单帧检测推理耗时，不能等同于整套系统实时 FPS。

### 对前端文案的直接约束

页面必须把四种状态分开：

1. **观察到**：模型在某帧检测到香烟、手部或行人。
2. **系统推断**：时序规则形成“持烟 / 抛掷 / 落地候选”。
3. **人工复核**：管理员确认或驳回事件。
4. **治理处置**：生成工单、到场清理并完成闭环。

因此不建议继续使用一个笼统的“检测置信度 92%”概括整起事件。更可信的呈现方式是：分阶段置信度、证据完整度、关联可靠度和人工复核状态分别展示。

## 2. 对现有页面的第一轮评价

### 可保留的优点

- 已有清晰的模块化导航、状态标签和卡片体系。
- 事件、证据、调度、闭环、复盘的产品链路基本齐全。
- Vue3、ECharts、Pinia 与统一设计令牌为后续重构提供了稳定底座。
- 1672×941 定宽缩放适合答辩投影，演示时不易崩版。

### 关键问题

#### 关键问题：产品主角错位

首页当前以宣传横幅、四个大数字、普通趋势图和热力图为视觉中心，最关键的“三段式行为证据链”只占右侧一张模糊图片。它更像通用城市治理后台，无法在第一屏回答“系统凭什么认为这是一次烟头乱扔”。

#### 重要问题：演示规模损害可信度

“在线设备 3842、在线人员 684、今日违规 1286”与 2–4 路摄像头的校园小范围试点不一致。即便标注“设计稿级”，评审仍可能把它理解为夸大。答辩默认应使用试点口径，并明确“模拟事件”。

#### 重要问题：事实与推断混在一起

现有事件详情把“三段式证据链校验通过”“轨迹连续”“处置建议”放在同一层，缺少原始观测、算法推断、人工结论之间的视觉边界。这会让系统显得武断，也不利于解释误报。

#### 重要问题：导航覆盖产品故事

七个一级模块、十七个管理页面适合完整后台，不适合短时间答辩。评审需要看到的是“发现 → 复核 → 派单 → 闭环 → 复盘”，而不是先理解系统组织架构。

#### 次要问题：视觉语言过于常见

蓝绿渐变、玻璃卡片、城市科技横幅和密集 KPI 是成熟但高度同质化的“智慧城市模板”语言。它缺少与烟头、时间序列、取证和可追溯性相关的独特视觉语法。

#### 次要问题：固定画布只适合展示

定宽缩放适合答辩屏幕，但文字随整体缩放会变小，真实日常使用时不够友好。后续若目标转向部署，应另做响应式工作台；当前阶段可暂时保留。

## 3. 建议的前端核心概念

### 设计命题：城市行为取证台

不再把网站设计成“看数据的大屏”，而是设计成一张可以逐层核验的数字取证桌：每个结论都能回到对应帧、时间戳、目标框、轨迹和人工操作记录。

建议用以下五步作为全站永久叙事：

`捕捉 Capture → 串联 Link → 研判 Verify → 调度 Dispatch → 复盘 Learn`

### 首屏建议

- 移除大面积宣传轮播，将首屏中心改为“最新待研判事件”。
- 中央主画面采用三联帧：持烟、抛掷、落地；三帧共享时间轴和轨迹线。
- 左侧只保留 3 个可信指标：待复核事件、证据完整事件、超时工单。
- 右侧显示“证据账本”：模型观察、规则推断、人工操作、工单状态按时间追加。
- 地图降为上下文层：告诉用户事件发生在哪里，不抢占证据主角位置。
- 所有模拟内容使用稳定、克制但不可忽略的“模拟数据”标识，不混充真实采集。

### 视觉方向建议

暂定方向名：**城市取证 / Civic Forensics**。

- 主底色：偏墨色的深海军蓝或暖灰白，不继续使用大面积糖果蓝渐变。
- 关键强调：烟蒂余烬橙红，用于候选事件与关键帧；冷青色用于可信轨迹；苔绿仅用于闭环完成。
- 图形语法：时间刻度、帧编号、坐标、虚线轨迹、证据编号、校验章，比普通插画更有项目辨识度。
- 卡片弱化装饰性投影，强化细边框、层级、对齐和证据编号。
- 数字不追求“大”，追求“可解释”：每个指标都能点击追溯到事件集合。

这一方向可以在现有 Vue 工程和设计令牌基础上渐进改造，不要求推翻技术栈。

## 4. 建议信息架构（讨论稿）

答辩主路径压缩为五个一级入口：

1. **证据总览**：今日待办、最新事件、三帧证据链、试点状态。
2. **事件研判**：事件队列、视频回放、轨迹叠加、确认/驳回及原因。
3. **治理调度**：从确认事件生成工单，派发、超时升级、清理前后对比。
4. **时空复盘**：地图、时段分布、重复发生点、治理前后变化。
5. **系统与模型**：摄像头、模型版本、阈值、用户、审计；作为后台入口弱化展示。

原 18 页不一定删除，可以并入上述五个入口的二级页面。这样既保留完整功能，又让答辩叙事更短。

## 5. 第一轮待用户确认的问题

以下问题会直接改变页面结构和视觉方向，需优先确认：

1. **网站第一目标是否仍是“答辩演示原型”？** 如果是，我会优先设计一条 3–5 分钟可讲完的故事线，而不是先追求完整后台效率。
2. **18 个页面是否仍是必须全部保留的硬要求？** 我建议保留功能但重组为 5 个一级入口；如果页数必须与既有材料一一对应，则采用“5 个主入口 + 18 个子页”的方式。
3. **能否接受明显改变当前蓝绿玻璃大屏风格？** 我的首选是“城市行为取证台”：更克制、更像证据工作台，余烬橙作为独特强调色；备选是保留浅色基调，只重做信息层级。
4. **答辩时是否会提供一段真实或半真实的测试视频？** 若有，事件研判页应以视频和三帧同步为核心；若没有，需要提前制作一套明确标注“模拟”的演示事件素材。
5. **演示时是否需要现场运行模型，还是只演示已生成事件？** 现场运行会增加“视频输入 / 推理状态 / 处理延迟”界面；只演示事件则可把精力集中在取证和闭环。
6. **人工复核在产品中是否是强制步骤？** 根据申报书目前证据强度，我建议候选事件必须经人工确认后才能进入正式工单，不能让算法结论直接等同于责任认定。
7. **主要展示屏幕是什么？** 请确认常用答辩分辨率（例如 1920×1080）以及是否只用电脑端；这决定是否继续把 1672×941 定宽缩放作为唯一布局策略。

## 6. 暂定决策（等待确认）

- 首页主角从“大盘指标”调整为“可复核证据链”。
- 默认演示采用校园试点口径，不使用千级设备和千级日事件数。
- 页面明确区分模型观察、系统推断、人工复核与治理处置。
- 保留现有 Vue3 工程作为实现底座，不继承其全部视觉表达。
- 在用户确认前不进入页面编码。

## 7. 2026-09-27 第二轮确认

### 用户已确认

- 产品目标改为真正投入校园日常使用，不再以答辩演示原型作为最高目标。
- 申报书只作为参考资料，产品设计可根据真实使用需求调整。
- 网站增加公开的长滚动 Landing Page，用连续章节介绍产品并引导不同用户进入平台。
- 管理端既有功能保留，但重组为五个一级入口：证据总览、事件研判、治理调度、时空复盘、系统与模型。
- 接受明显改变当前蓝绿玻璃大屏风格，采用更有辨识度的设计语言。
- 后续需要真实或半真实测试视频，并需要支持现场运行模型。
- 当前只编写设计文档，不进入页面代码开发。

### 产品范围修订

管理员端不能独立构成完整产品。平台正式划分为：

1. 公开官网 / Landing Page。
2. 校园公众端。
3. 环卫作业端。
4. 管理控制台。

其中公众端用于问题上报、进度查询和治理信息；环卫作业端用于移动工单、导航、清理前后拍照和闭环；管理控制台负责证据研判、调度、复盘和系统运维。完整证据不能向普通公众开放。

### 对附件示例的处理

用户提供的腾讯云首页截图仅作为页面形态参考。采用其“吸顶导航 + 长滚动分区 + 明确行动入口”的结构特征，不复制其云厂商品牌、蓝色飘带、产品促销卡片或导航密度。

## 8. 2026-09-27 第三轮确认

### 用户已确认

- 校园公众端允许师生主动上报问题并上传照片。
- 公众端增加摄像头功能，支持现场拍照并进行烟头识别。
- 允许匿名上报。
- 环卫作业端可同时面向普通浏览器、PWA、微信和企业微信使用。
- 视频输入同时需要固定摄像头实时流和上传视频文件。

### 设计结论

- 拍照识别定位为上报辅助，不作为能否提交的门槛；模型漏检时用户仍可上报。
- 匿名提交生成独立查询码和进度链接，避免匿名用户提交后无法获得处理结果。
- 摄像头实时流和上传文件统一进入“分析任务”，使用同一套证据生成、事件研判和人工复核界面。
- 环卫作业端采用共享业务内核的移动 Web/PWA，微信与企业微信是访问容器或后续能力接入点，不单独复制一套工单系统。
- 匿名上报需要轻量防滥用机制，但具体采用验证码、短信或校园网限制仍待确认。

## 9. 2026-09-27 第四轮纠偏与确认

### 关键纠偏

- 项目研究与产品核心是**识别人扔烟头的动作**，不是识别静态烟头。
- 香烟、手部和行人目标检测只是形成行为证据链的前置能力，最终候选事件必须依赖连续视频、时序阶段和人—物关联。
- 单张照片无法证明抛掷动作。用户端拍照只用于补充烟头落地点、环境卫生状态或清理结果；行为线索应通过短视频、上传视频或固定摄像头实时流获取。

### 覆盖前一轮的最新决定

- 前一轮“允许匿名上报”的决定已撤销。
- 举报人必须注册登录平台后提交，后台授权角色可以查看举报人信息。
- 第一期自动识别范围聚焦扔烟头动作，不扩展垃圾堆积、垃圾桶满溢等其他自动识别类别。
- 登录用户可以补充举报内容；在管理人员受理前可以撤回，受理后只能申请撤回。

### 协作要求

- 后续不得把“烟头目标检测”“扔烟头行为识别”和“现场卫生照片”混为同一能力。
- 需要用户决定的问题应一次性集中提出，不再多轮零散追问。

## 11. 2026-09-27 产品范围升级：信阳市区域治理

### 范围纠偏

- 产品面向信阳市各县区、街道、网格和公共区域，不局限于信阳学院或校园。
- 校园只是可选试点场景之一。此前文档中基于“校园用户、校园地图、校园统一认证”的默认假设全部由本节覆盖。
- 平台区域层级调整为“市级—县区—街道/乡镇—网格/点位”，账号、事件、摄像头、工单和统计均需绑定区域权限。

### 端的最终建议

建设“一个公开门户 + 四个业务端”，合计五类前端体验：

1. **公开官网 / Landing Page**：介绍产品、规则依据、隐私边界和各端入口。
2. **市民用户端**：实名注册、视频线索上报、现场材料补充、进度查询和申诉。
3. **环卫作业端**：接单、导航、清理、拍照、异常说明和闭环。
4. **治理管理端**：市/县区/街道分级研判、调度、复盘、设备与模型管理。
5. **执法协同端**：供有权限人员核验线索、身份和规则依据，记录告知申辩、处理决定及结果回传。

AI 与设备运维作为治理管理端的角色模块，不额外建设独立端；大屏只是展示模式，不是独立业务端。

### 约束与处罚机制

- 没有实际处置后果，仅靠宣传页面不足以形成约束，因此系统必须连接环境清理、巡查和合法执法流程。
- 信阳市现行市容环境卫生管理条例明确禁止在公共场所乱扔烟头，并设置责令停止、清除或补救以及相应罚款机制。
- 平台不能自动处罚，也不能把行为识别直接等同于行为人身份确认。
- 建议采用“治理提醒—现场纠正—执法线索—依法处理”的四级处置。
- 无法合法、可靠确认行为人身份时，只生成清理工单、热点分析和巡查任务，不生成个人处罚。
- 执法协同端必须保留人工核验、规则依据、告知、陈述申辩、处理决定与审计记录。

### 覆盖旧清单的新默认方案

- 身份认证改为手机号实名注册，并预留统一政务身份认证；不再使用学号/工号和校园统一认证作为全局方案。
- 地图改为信阳市行政区划与街道/网格地图，不再使用校园平面图作为主地图。
- 初期部署范围由“2–4 路校园摄像头”改为“选择一个县区或若干街道试点，设备数量按实际点位配置”。
- 第一阶段闭环增加执法线索移送、告知申辩和处理结果回传。
- 官网素材改用获得授权的信阳城市公共空间场景，校园素材仅作为一种场景。

### 尚需外部主管部门确认但不阻塞前端设计的事项

- 首批试点县区、街道/网格和摄像头点位。
- 实际参与的市容环境卫生主管部门、城市管理执法单位和环卫作业单位。
- 各类证据的保存期限、移送格式和处罚办理系统对接方式。
- 实名认证最终采用手机号、政务认证或两者结合。

前端方案可先按上述默认边界继续设计，这些事项在真实部署前由项目方与主管部门确定。

## 12. 2026-09-27 三端收敛与用户端重点

### 用户提出的硬约束

- 项目最多支持三个端，市民用户端算其中一个。
- Landing Page 不单独计算为端，作为市民用户登录前的介绍背景。
- 环卫作业与治理管理必须合并为一个端。
- 用户端需要重点开发，除举报外必须包含科普和更丰富的正向参与功能。

### 最终三端

1. **市民用户端**：登录前为 Landing Page，登录后包含科普、合规吸烟点地图、视频行为线索上报、现场卫生随手拍、文明任务、治理进度、积分和申诉。
2. **治理作业端**：同一端内提供桌面管理工作台和移动环卫工作台，依靠角色权限与响应式布局区分。
3. **执法协同端**：保持窄范围，专门承担已复核线索、身份与规则核验、告知申辩和处理结果回传。

公开官网、环卫移动页面、AI/设备运维和大屏均不再单独计算为端。

### 对附件构想的判断

- 采纳区域选择、附近合规吸烟点、文明任务、科普、用户记录和五项底部导航。
- “随手拍”仅用于现场卫生状态；扔烟头动作识别仍必须依赖连续视频。
- 积分用于知识学习、设施纠错、志愿活动和核实后的有效线索，不按举报数量直接排名。
- 不通过高额积分诱导追拍他人，不公开被举报对象信息。

### 用户端优先信息架构

底部导航固定为：首页、地图、上报、任务、我的。科普作为首页重点内容并在任务中心形成连续学习体验；“上报”居中突出，但首次使用前必须展示安全、真实性与隐私提示。

## 13. 2026-09-27 第三端升级与竞赛评审

### 第三端升级

- 第三个端由“执法协同端”升级为“平台管理与执法协同端”。

- 平台管理与执法处理虽然共用一个端，但默认使用不同角色和权限；账号管理员不能自动获得执法决定权限。

### 评委视角结论

- 选题社会价值和完整产品潜力较强，三端收敛是正确方向。
- 当前 Vue 工程和行为识别实际完成度不足以支撑规划中的全部能力，现阶段不宜以“完整城市治理平台”自居。

- 数字媒体竞赛应以市民用户端、长滚动叙事、科普传播和原创视觉为主，管理后台只作为系统支撑。
- 两类比赛必须使用不同的演示叙事：Web 强调工程，数媒强调体验与传播。
- 国赛竞争力取决于行为级验证、真实业务闭环、用户测试、原创合规档案和稳定演示五项硬证据。

## 15. 2026-09-27 关键反对意见与最后一批确认问题

### 必须明确反对或修正的内容

#### 1. 反对把“面向信阳市”包装成“已经完成全市部署”

产品架构可以支持市—县区—街道—网格，但比赛作品和现阶段文案应写成“面向信阳市多区域治理、以单个区域试点验证”，不能暗示已经接入全市摄像头、城管和环卫系统。否则评委会要求提供合作协议、真实点位、运行记录和治理数据，项目无法自证。

#### 2. 反对把市民追拍陌生人作为核心采集方式

扔烟头动作需要连续视频，但鼓励普通用户追拍他人会产生安全、隐私、对抗和恶意举报风险。固定摄像头或授权测试视频应是行为识别的主要来源。市民端以科普、合规设施地图、现场卫生上报和治理反馈为主；视频线索上传作为次级入口，必须提示不要尾随、拦截或公开传播。

#### 3. 反对“识别成功就自动处罚”

算法只能生成候选事件。即使动作成立，也不等于已经确认法定身份。没有现场或合法身份核验时，只能进入清理、热点分析和巡查流程。处罚必须由有权限人员人工核验证据、身份和规则依据，并提供告知与申辩。

#### 4. 反对管理员查看用户密码

平台管理与执法协同可以放在同一个端，但超级管理员只能重置密码、强制退出和查看登录审计，不能查看明文密码。账号管理、事件审核和执法决定必须使用不同权限。

#### 5. 反对用举报数量做积分排行榜

这会刺激刷量、重复举报、跟拍和隐私侵犯。积分只奖励核实后的有效贡献、科普学习、设施纠错和志愿活动；举报数量不公开排名。

#### 6. 反对在没有权威数据时上线“合规吸烟点”

地图点位可能被误认为官方许可。点位必须由主管单位确认开放状态、边界和维护责任；没有可靠数据时可以做“烟蒂投放设施”地图或比赛演示数据，但要明确标注，不能冒充官方许可。

#### 7. 反对同时把三个端都做成庞大独立工程

三个端是三种产品入口，不代表维护三套互不相干的技术系统。建议共享一个后端、账号体系、事件状态和设计系统；前端可按角色分包或分入口构建。这样既满足三端展示，也不会让团队被重复开发拖垮。

#### 8. 反对继续优先重建旧18页

旧页面可以作为功能库，但比赛版本必须优先跑通一条黄金路径。先完成约12个核心页面，再决定哪些旧页面值得迁移。

# 烟踪智治 · 竞赛风险逐项解决规划

日期：2026-09-27  
目的：把评委担忧转化为可执行设计与可验收证据，按顺序逐项消除。  
当前阶段：规划，不在本文件中实施代码。

## 1. 为什么当前工程完成度是 4/10

这个分数只评价当前工作区能够现场运行和验证的内容，不评价构想质量。

### 已有成果

- 已建立 Vue 3、TypeScript、Vite、Element Plus、ECharts 与 Pinia 工程。
- 已完成登录页和总览页迁移。
- 已整理 18 页旧设计稿、统一设计令牌和模拟数据契约。
- 已实现可重复生成事件、工单、趋势和建议的前端模拟引擎。
- 已形成较完整的产品设计、三端架构和竞赛叙事。

### 当前缺口

- 页面注册表中只有总览页标记为已迁移，其他业务路由仍使用 `PagePlaceholder.vue`。
- 工作区没有后端服务目录、数据库迁移、真实 REST API 或 WebSocket 服务。
- 登录、事件、工单、用户、权限和审计仍为本地模拟状态。
- 三端尚未形成真正可登录、可流转的三个运行入口。
- 没有端到端自动测试、部署脚本、故障恢复验证和真实用户测试。
- 旧 18 页静态设计稿不能等同于已完成的工程系统。

因此 4/10 的含义是：**工程骨架和两页展示已经存在，但业务闭环尚未实现。**

## 2. 为什么当前算法可信度是 3.5/10

### 已有成果

- 工作区存在约 6.3 MB 的 `best.pt` 权重文件。
- `data.yaml` 明确包含 `cigarette`、`hand`、`person` 三个目标类别。
- 论文材料记录了目标检测指标，并提出持烟、抛掷、落地三阶段证据链。
- 研究方案已经意识到行人跟踪、人—物关联和状态机的重要性。

### 当前缺口

- 工作区没有训练脚本、推理脚本、视频处理程序或可复现环境文件。
- 没有 ByteTrack、光流、人—物关联和三阶段状态机的实际代码。
- 前端 `mock/engine.ts` 明确说明 AI 管道尚未实现，当前证据帧、轨迹和置信度由模拟生成。
- `paper_work/audit.json` 标记文稿尚未达到提交状态，并列出独立视频事件标注、行人 ID 标注、消融实验、关联对比和整条流水线测速等缺失项。
- 已记录的 mAP 是目标检测指标，不能直接回答“完整扔烟头事件识别得准不准”。
- 训练结果来自既有材料转录，尚未在当前工作区重新运行验证。

因此 3.5/10 的含义是：**已有目标检测模型和行为识别设计，但完整行为算法尚未形成可复现证据。**

## 3. 解决顺序

不同时补全部问题，按竞赛风险从高到低推进：

1. 核心行为识别最小闭环。
2. 三端共享的真实业务状态链。
3. 用户端与视觉叙事。
4. 权限、隐私、地图和素材合规。
5. 测试、性能、部署和答辩兜底。

每一阶段必须达到验收门槛后再扩大功能。

## 4. 风险一：行为识别只有设计，没有运行链路

### 4.1 最小可行算法范围

第一版不追求覆盖所有复杂环境，只先打通：

```text
视频输入
→ YOLO 检测香烟、手部、行人
→ 为行人分配连续轨迹 ID
→ 计算香烟与手部/行人的空间关系
→ 根据连续帧变化形成持烟、抛掷、落地候选
→ 输出事件 JSON、三张关键帧和视频片段
```

### 4.2 数据设计

建立独立视频测试集，训练图片不能直接充当事件测试数据。至少覆盖：

- 正常扔烟头。
- 手部运动但未抛掷。
- 烟头短暂遮挡。
- 多人交叉。
- 远距离小目标。
- 夜间或低照度。
- 镜头抖动。
- 已有烟头出现在地面，但没有抛掷动作。

每段视频标注：事件是否发生、三阶段时间、关联行人、烟头轨迹、失败原因。

### 4.3 第一阶段指标

- 事件级准确率、召回率、F1。
- 每小时误报次数。
- 三阶段分别的检出率。
- 人—物关联正确率。
- 端到端处理延迟，而非只报单帧推理耗时。

### 4.4 验收门槛

- 至少有一条从真实视频产生的事件，不由前端模拟生成。
- 事件包含非空关键帧、严格递增时间戳、轨迹和来源视频。
- 同一视频重复运行能够获得可解释的一致结果。
- 至少保存三种失败案例，并能说明失败原因。

完成本阶段后，算法可信度可从 3.5 提升到约 6；加入独立测试、消融实验和复杂场景评估后，才有资格向 7.5–8 提升。

## 5. 风险二：三端可能停留在静态页面

### 5.1 比赛最小业务闭环

只选择一条黄金路径作为第一优先级：

```text
市民上传视频或固定摄像头产生候选事件
→ 治理作业端审核员确认
→ 系统生成待派发工单
→ 移动工作台接单并上传清理后照片
→ 审核员确认闭环
→ 市民端收到完成通知
→ 满足条件时移送平台管理与执法协同端
```

### 5.2 共享状态模型

三个端必须读取同一份后端数据。核心状态建议为：

- 分析任务：上传中、排队中、分析中、证据生成中、待复核、完成、失败。
- 事件：候选、待复核、已确认、已驳回、已移送。
- 工单：待派发、待接单、处理中、待验收、已闭环、异常。
- 用户上报：已提交、分析中、已受理、处理中、已完成、不予受理、申诉中。
- 执法线索：待核查、需补充、处理中、不予处理、已处理。

### 5.3 后端最小模块

- 认证、会话和角色权限。
- 视频上传与分析任务。
- 事件与证据查询。
- 工单创建和状态流转。
- 用户上报、补充、撤回和申诉。
- 账号、登录审计和敏感操作审计。
- WebSocket 或事件轮询，用于状态更新。

### 5.4 验收门槛

- 刷新浏览器后状态不会恢复为初始模拟值。
- 三个角色登录后看到不同菜单与数据范围。
- 一个端完成操作后，另一个端可以看到真实状态变化。
- 网络失败、重复提交和权限不足都有明确界面状态。
- 比赛演示能够在 3–5 分钟内完整跑完黄金路径。

完成本阶段后，工程完成度可从 4 提升到约 6.5；补齐核心测试、部署、日志和故障恢复后，才可能达到 8。

## 6. 风险三：范围太大导致每项都浅

### 6.1 第一优先级页面

只把以下页面列入比赛必须完成范围：

#### 市民用户端

- Landing Page。
- 注册登录。
- 视频行为线索上报。
- 我的上报与处理进度。
- 合规吸烟点与科普首页。

#### 治理作业端

- 证据总览。
- 事件研判。
- 工单调度。
- 移动作业详情与完成提交。

#### 平台管理与执法协同端

- 账号、角色与登录审计。
- 已复核线索详情。
- 处理结果回传。

### 6.2 延后功能

- 复杂积分商城。
- 大型排行榜。
- 全量 18 页重建。
- 高级 AI 参数调优。
- 多层级大屏模板。
- 复杂自动决策建议。

这些功能可以保留在路线图中，但不应占用核心闭环完成时间。

## 7. 风险四：隐私、地图和素材合规

### 7.1 隐私设计

- 市民实名信息、被举报对象画面和登录审计分开授权。
- 环卫人员默认不查看举报人实名和完整行为视频。
- 对外展示自动模糊人脸、车牌和无关个人信息。
- 用户上传前说明用途、范围、保存期限和申诉渠道。
- AI 不自动确认身份或自动处罚。

### 7.2 地图设计

- 比赛材料使用来源明确、允许公开展示的地图。
- 标注地图来源和审图信息；若使用自绘街区示意图，明确它不是精确行政地图。
- 不擅自修改行政边界，不使用来源不明的地图截图。

### 7.3 素材台账

为每个字体、图标、照片、视频、音乐、模型、数据集和 AI 生成资产记录：来源、许可证、修改方式、使用页面和作者贡献。

## 8. 风险五：视觉像模板，数字媒体竞争力不足

- 使用“帧、时间戳、轨迹、证据编号、闭环印记”构建统一视觉语法。
- Landing Page 用一条真实事件贯穿滚动过程，不堆普通宣传卡片。
- 市民端强调正向参与、科普与结果反馈，不营造监视感。
- 治理作业端优先信息效率，不复制用户端的宣传动效。
- 生成一套原创图标、动效和城市公共空间插图，并保存创作过程。
- 通过可用性测试证明设计改善，而不只凭主观审美评价。

## 9. 风险六：现场演示不稳定

准备三层兜底：

1. 现场摄像头或实时视频。
2. 本地上传测试视频。
3. 明确标注“预生成演示”的固定事件。

三条路径必须进入相同的研判与工单界面。兜底不是伪造实时结果，而是保证网络或模型环境异常时仍能展示业务链。

## 11. 当前立即执行的规划重点

下一阶段只解决两件事：

1. 定义并验证“真实视频 → 行为事件”的最小算法输入输出。
2. 定义“三端共享事件 → 工单 → 闭环”的数据和页面状态。

在这两件事完成前，不继续扩充新端、排行榜、积分商城或更多管理页面。

## 12. 产品边界的反对意见

- 面向信阳不等于已经全市落地；比赛表述采用“面向信阳多区域治理的试点原型”。
- 固定摄像头和授权视频是行为识别主要来源，市民视频只作为次级线索入口。
- 合规吸烟点需要权威数据；没有官方确认时只能展示演示点位或烟蒂设施。
- 三端共享后端、账号、事件状态和设计系统，不建设三套重复工程。
- 管理员不查看明文密码，AI 不自动处罚，举报数量不进入公开排行榜。

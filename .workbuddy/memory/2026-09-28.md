  —— 判断"源能不能用"必须用 pip 实测，不能只看 curl。
  （显式 `+cu128` 本地版本号可强制选中 CUDA 轮子，避免 TUNA 上的同名 CPU 版被装上）。

**踩坑：后台任务清理会连带杀掉 `nohup` 的下载进程**
先用 `nohup curl ... &` 起下载，再 `TaskStop` 另一个后台任务时，curl 被一起清掉了，
文件停在 92MB 不动（表现为「速度 0 KB/s」）。
→ **正确姿势：把「下载 → 校验 → 安装」放在同一个后台任务里串行执行**，不要跨任务传递长进程；
   必要时 `curl -C -` 断点续传。

### 七、★ 市民端「上传即检测」核实（用户提问）

**结论：链路是通的，而且是真检测。** 浏览器内实测（CDP 里发真实 fetch）：

```
http 200 · 浏览器端到端 225ms · 服务端 total 36ms · infer 32ms
verdict=疑似烟头目标 · count=4 · confidence=84.6%
```

链路：`CitizenAppView.onFile()` → `POST /api/v1/public/ai/inspect`（FormData）
→ `backend/app/routers/inference.py` → `best.pt`（GPU device=0）
→ 返回结构化 AI 报告（verdict / 置信度 / 三段式**推断**标注 / 证据链不完整提示 / 免责说明）。

**关键事实与坑（重要，避免重复排查）**
1. **接口本身只要 30–60ms**。我一度测到「每次 30–60 秒」，全是假象：
   - 用 **curl / python-requests**（沙箱内的 HTTP 客户端）打 `127.0.0.1:8000` 时，客户端要等 30–60s 才拿到响应，而**服务端 timings 只有 59ms**；经 Vite 代理（5180）也一样。
   - 换到**真实浏览器内 fetch**：225ms。→ **沙箱会惩罚本地 HTTP 客户端，不要用它测延迟**，要用浏览器内 fetch。
2. **`import ultralytics` 本机实测 3.5 秒**（不是在 yolo 环境 47s；那是注释里的旧数据）。
   但**不预热的话每个新进程首次请求要额外付这个钱**，所以预热必须有。
   已在 `main.py` lifespan 里调 `await asyncio.to_thread(inference.warmup)`（另一方会话又加了
   `settings.ai_warmup` 开关与 `/public/ai/status` 端点）。启动日志应出现「AI 预检已预热：best.pt · device=0」。
3. **后端必须跑在装了 ultralytics 的环境里**：默认 `envs/default` 没有 → 接口返回 503
   `AI_RUNTIME_MISSING`，前端会**静默回退到本地假预检**（用户会以为"检测了"其实没有）。
   我已在 `envs/yolo`（自带 CUDA torch + ultralytics）里补装后端 requirements，用它跑 uvicorn 即可。
   项目自带的 `backend/start.bat` 会在 backend/ 下自建 `.venv`（会再下一次 torch，慢）。
4. **只能跑一个后端实例**：两个实例共用一个 SQLite（`backend/data/yanzong.db`）会互相写锁
   （日志里大量 `database is locked`，SQLAlchemy 默认 5s 超时）。`db.py` 未设 WAL/busy_timeout，我没改（属另一会话模块）。
5. **前端预检超时 3.5s 偏紧**：冷启动/未预热时会超时并静默回退。预热后 225ms，够用。
